## 1. Summary

The correction pipeline is sound. The N-Questie callbacks are registered at file load (TOC lines 88–91) and are only *executed* inside `QuestieCorrections:Initialize()`, after `QuestieInit:LoadBaseDB()` has turned the database strings into tables. I ran the real WotLK database through the real `_LoadCorrections` and `QuestieCompat.LoadCorrections` with `Is335 = true` (harness described in §6). Quest 1203 and all eight Dustwallow quests come out with the intended values and nothing else changes. The compiler then completes without errors.

There are no blockers in the Lua that PR #6 and PR #7 add. The real problems are in process and test architecture:

- Cache invalidation relies on a manual revision bump in a different file.
- Inherited CI fails on every stacked PR because PR #4 is not in the stack.
- No CI test exercises the real 3.3.5a correction path.
- PR #3 has dropped nine of PR #2's documentation commits, so the stack does not merge cleanly.

Verified correct (no action needed):

- **Q3, quest 1203.** The callback returns only `[keys.objectives]` and `[keys.objectivesText]`. It shallow-copies the objectives table, so slots 1, 2, 4, 5 and 6 are preserved, and it does not mutate the original. It is guarded on `#objectives[3] == 1` and on the item being `33110`. Real-DB result: `req=30 lvl=35 obj={nil,nil,{{3853}}} start={{4792}} pre={1206}`. `startedBy`/`finishedBy`, `preQuestSingle` (13), `preQuestGroup` (12) and `exclusiveTo` (16) are untouched. The only other correction for 1203 in any layer is `reputationReward` in `classicQuestReputationFixes.lua:3399`, which does not overlap.
- **Q4, Dustwallow.** The keys used are `questKeys.requiredLevel` (4) and `questKeys.questLevel` (5), both checked against `Database/questDB.lua`. Real-DB results: 1166/1168/1169/1170/1171 `38/43`, 1172 `38/45`, 1205 `35/45` (min unchanged and not emitted), 1252 `30/40` (min unchanged). Objectives, starters and `preQuestSingle` (for example 1252 keeps `{11123}` from `wotlkQuestFixes.lua:126`) are intact. No level corrections for these IDs exist in the Classic, TBC or WotLK layers, so the source guards match.
- **Colour.** Colour is still derived from the level. `QuestieLib:PrintDifficultyColor` and `GetDifficultyColorPercent` (`QuestieLib.lua:40–90`) compute `level - QuestiePlayer.GetPlayerLevel()` together with `GetQuestGreenRange("player")`. Nothing forces a colour.
- **ID collisions.** None. The N-Questie IDs (2001, 1203, 1166–1172, 1205, 1252) are disjoint from each other and from `Compat/Corrections.lua` (12372, 12435).
- **Composition.** `QuestieCompat.LoadCorrections` runs the callbacks in registration (TOC) order and evaluates each `corrections()` just before it is applied. Each callback therefore sees earlier results. `_LoadCorrections` replaces whole fields, which is why the 1203 callback has to copy the objectives itself, and it does.
- **SavedVariables.** The first load after upgrading has `nQuestieDataRevision == nil`, which triggers one rebuild. The TOC version change `9.5.1 → 9.5.1.1` also triggers one. Rolling back to stock Questie changes the version string, so stock rebuilds. The stray `nQuestieDataRevision` key is harmless. The revision is written only after `Compile()`, so an interrupted compile retries on the next login.

## 4. Integration risks (need verification)

| # | Severity | Risk | Why it matters | Verification |
|---|---|---|---|---|
| R1 | Medium | Objective index alignment. Questie maps quest-log objective *n* to `ObjectiveData[n]` (`QuestieQuest.lua:1101, 1469`). `ObjectiveData` is built in a fixed order: creatures, objects, items, reputation, kill credit, spells (`QuestieDB.lua:1205–1290`). The server orders RequiredNpcOrGo1–4 and then RequiredItemId1–6. An overlay that writes objectives in server order across types could attach pins to the wrong log line. | Matters for future objective corrections and the 151 NPC candidates. Not a bug in #6 (single item). | In game, on a mixed NPC + item quest, compare the tracker lines with the pins. |
| R2 | Medium | The PR #2 loader overwrites any ID in `custom.quests` without checking whether the quest already exists. If upstream later adds 2001, or a generated record collides with a stock ID, the stock record is replaced wholesale (objectives, text, triggerEnd and so on). | `NQuestieCustomQuestLoader.lua` `validQuest()` has no `QuestieDB.questData[id] == nil` check. | Add an "add only" guard plus a test where the ID already exists. |
| R3 | Medium | The source guards fail silently. If a later upstream correction changes the base values, the N-Questie fix is skipped without any log line, so the problem is invisible in game. | Both new callbacks just `return {}` or skip. | Emit `Questie:Debug(Questie.DEBUG_DEVELOP, …)` for each skipped guard. Have the 335 harness assert that every expected correction applied. |
| R4 | Low | Real 3.3.5a timing. Corrections run inside the init coroutine with `coYield()` between stages. The harness replaces `coroutine.yield` with a dummy, so frame-split timing, `/reload` mid-compile and taint are not covered. The N-Questie code adds no frames, hooks or secure calls, so the taint exposure is nil. | Mock gap. | One clean login plus one `/reload` during the "Updating quests" stage. Expect a rebuild on the next login. |
| R5 | Low | `IsComplete` and the IP-gated availability of the Dustwallow quests are decided server-side (Individual Progression scripts). A correct level does not make a quest visible or eligible. | Expectation management for QA. | Check on a character at the right IP stage. |
| R6 | Low | The 1203 objective text was rewritten to "Bring a Moonsteel Broadsword to Jarl in Dustwallow Marsh." The original names the NPC "Swamp Eye" Jarl and Swamplight Manor. | It is unclear whether this is the literal server `Objectives` text or a paraphrase. | Developer to confirm against `quest_template.Objectives`. |
| R7 | Low | PR #7's synthetic fixture gives all eight quests the same starter and objective tables (`{{4792}}`, `{{3853}}`), so it cannot detect a field mix-up between quests. | Weak fixture. | Covered by the real-DB harness (C2). |
