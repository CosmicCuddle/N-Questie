## New source-specific synthetic 1-to-0 and 1-to-nil insight

Authentic original QuestLogCache.GetNewObjectives compares only `oldObj.raw_numFulfilled`, `oldObj.raw_text`, `oldObj.raw_finished`, `numRequired` and `type` to decide whether to **reuse the old objective table**; it does not inspect the old normalized `numFulfilled` or `finished`. In `CheckForChanges`, an `isComplete == 1` quest-state change forces `finished=true` and `numFulfilled=numRequired` **on the reused table**, deliberately preserving separate `raw_*` values.

If a **fabricated quest** later changes `isComplete` from `1` to `0` while the fabricated native objective text/progress/finished flags remain identical, the method detects the quest completeness metadata difference but reuses the old **already forced** objective table. It does **not** undo the forced normalized values when `isComplete ~= 1`; thus normalized `numFulfilled/finished` remain visually complete while `raw_numFulfilled/raw_finished` reflect incomplete progress. A separate deliberately fabricated `1`→`nil` change (original 335 Compat title adapter preserves nil for objectives-present quests) has the same source-level behaviour. Once fabricated raw progress/text genuinely changes, `GetNewObjectives` creates a new normalized objective table and the normalized values reflect the raw data again. `RemoveQuest` clears the stale cache and a fresh import also restores raw values.

**This is a conditional source-level normalization/cache-reuse behaviour under fabricated inputs.** It does NOT establish that the native 3.3.5a API can emit `1→0` or `1→nil` with unchanged raw objectives, that `WasComplete` ever sees it, that a real player observes wrong counts, or that any production patch should be made.
